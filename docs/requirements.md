# このプロダクトで成し遂げること

## 目的

自宅に設置したPanasonic i-PROネットワークカメラ（WV-S1531L、WV-S3530）のSDカード録画を、カメラの公式CGI（[protocol.md](protocol.md)）で定期的に取得し、1動画を1ファイルとして保存する。保存先はローカルディレクトリまたはAWS S3。コンテナのワンショット実行（CLI、K8sのCronJobなど）を想定し、実行のたびに「前回の続き」から取得する。

## 基本動作

1回の実行は、カメラごとに次を繰り返す。

1. 取得位置（カーソル）を保存先から読む
2. カーソルより新しい録画のリストを取得する（`get_mp4_list`）
3. 古い順に1件ずつ、録画をダウンロードして保存先へ書く（`get_mp4_file`）
4. 保存に成功したら、カーソルを進めて保存先へ書く

- カーソルは「最後に保存した録画の連番と`end_time`」。リストは`Datafrom=カーソルの時刻`で検索し、連番がカーソル以下のものは除外する（`Datafrom`は指定時刻にかかるファイルを含むため、境界の1件が重複する）
- 1回の検索は最大100件。100件に達したら、最後の`end_time`で再検索して続きを取得する
- 録画を保存した後、カーソルを進める前に異常終了しても、次回は同じ録画を同じキーで上書き保存するだけで済む（冪等）
- 1件の保存に失敗したら、そのカメラの処理はその回で打ち切る（カーソルは進めない）。他のカメラの処理は続け、最後に1台でも失敗していれば非ゼロの終了コードで終了する
- プログラム内ではリトライしない。失敗は次回の実行（CronJobやコマンドの実行間隔）に任せる。同じ録画で失敗し続けても、飛ばさずに止め続ける（原因調査を促す）
- カメラは同時に1つの検索・ダウンロードしか受け付けない（[protocol.md](protocol.md)）ため、カメラ単位で直列に処理する
- 初回実行（カーソルが無い）は、現在から`FETCH_INITIAL_LOOKBACK`（既定24時間）さかのぼった時刻から取得する

## 保存先

保存先は`DEST_URL`で指定する。取り込みの処理は保存先の種類によらず共通で、保存先ごとに次の3つの操作だけが異なる。

- 録画ファイルの書き込み
- カーソルの読み出し
- カーソルの書き込み

| 保存先 | `DEST_URL`の例 | 録画のキー | カーソルの置き場所 |
|---|---|---|---|
| ローカルディレクトリ | `file:///data` | `{カメラ名}/{yyyy}/{yyyymm}/{yyyymmdd}/{ファイル名}` | `_state/{カメラ名}.json` |
| AWS S3 | `s3://bucket/prefix/` | 同上（プレフィックス配下） | `{prefix}_state/{カメラ名}.json` |

- 録画のファイル名は、カメラが返す`{連番}_{yymmddHHMMSS}_{種別}.mp4`をそのまま使う。日付のディレクトリは、ファイル名のローカル時刻から決める
- 録画はストリーミングで書き込む。ローカルは一時ファイルに書いてからrenameで確定し、S3はマルチパートアップロードで送る。カメラからの応答を丸ごとメモリに載せない
- 圧縮はしない（約20%縮むが、削減は月数ドル規模で、直接再生できなくなるため）。保管料はS3のライフサイクル（安価なストレージクラスへの移行）で抑える

### カーソルの保存場所（CronJob等でローカルに永続ストレージが無い場合）

カーソルを保存先に置く。S3なら、録画とは別プレフィックスの小さなJSONオブジェクト（`_state/{カメラ名}.json`）にする。これにより、CronJobのPodにPVCが不要になり、Podが毎回まっさらでも、前回の続きから取得できる。

- オブジェクトのメタデータではなく本文に持つ。S3のメタデータは更新にオブジェクトのコピーが必要で、本文の方が単純
- 録画のプレフィックスとは分ける。録画側にライフサイクルの有効期限を設定しても、カーソルが消えない
- カーソルが失われても、録画のキーが固定なので、時間をさかのぼって再取得するだけで再アップロードされるだけ（二重保存にならない）。復旧は`FETCH_INITIAL_LOOKBACK`で制御する
- 同時に2つ実行された場合は、S3の条件付き書き込み（`If-Match`/`If-None-Match`）でカーソルを更新し、競合した側が中断する。ローカルディレクトリの場合はロックファイルで排他する
- K8sではCronJobの`concurrencyPolicy: Forbid`も併用する（プログラム側の排他は保険）

## 実行環境に求めること

- カメラのHTTP（LAN内）に到達できるネットワーク上で実行する
- 保存先がローカルディレクトリの場合のみ、書き込み可能な永続ディレクトリが必要
- 保存先がS3の場合、永続ストレージは不要
- 実行環境（K8sのManifest、CronJobなど）の定義はこのリポジトリに置かない

## リポジトリの責務

このリポジトリに置くのはプログラム（ソース、テスト、コンテナイメージのビルド定義）のみ。実行環境の定義は別のリポジトリで管理する。

## 環境変数

カメラ名（`CAMERAS`の要素）は`[a-z0-9_]`のみとし、保存先のパスに使う。カメラごとの変数名には、カメラ名を大文字にしたものを使う。

| 変数 | 必須 | 既定値 | 内容 |
|---|---|---|---|
| `CAMERAS` | ○ | - | 対象カメラ名のカンマ区切り（例: `camera1,camera2`） |
| `CAMERA_<NAME>_HOST` | ○ | - | カメラのホスト（必要ならポート付き） |
| `CAMERA_<NAME>_USER` | ○ | - | Basic認証のユーザーID |
| `CAMERA_<NAME>_PASSWORD` | ○ | - | Basic認証のパスワード |
| `DEST_URL` | ○ | - | 保存先（`file:///path`または`s3://bucket/prefix/`） |
| `DEST_S3_ENDPOINT` | | 未設定 | S3互換エンドポイントを使う場合のURL |
| `FETCH_INITIAL_LOOKBACK` | | `24h` | カーソルが無いとき、現在からさかのぼる期間 |
| `FETCH_MAX_FILES` | | `0`（無制限） | 1回の実行で保存する最大件数（実行時間の上限対策） |
| `FETCH_HTTP_TIMEOUT` | | `60s` | カメラへのHTTPリクエストのタイムアウト |
| `LOG_LEVEL` | | `info` | `debug`/`info`/`warn`/`error` |
| `LOG_FORMAT` | | `json` | `json`/`text` |

S3の認証とリージョンはAWS SDKの標準の環境変数（`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_REGION`など）に従う。

## 対象外

- ライブ映像の取得・配信
- カメラ設定の変更
- 動画の圧縮・再エンコード・解析
- 常駐プロセス（デーモン）化
- 手持ちの2機種以外の動作保証（動作確認は実機のみ）

## 認証情報の取り扱い（publicリポジトリのため）

実ホスト・ユーザー・パスワード・AWSキーをコミットしない。次を実施する。

- 認証情報は環境変数でのみ受け取る。ファイルに書く設定方式は用意しない
- サンプルは`.env.example`に置き、値はダミー（`changeme`、`*.example.invalid`）にする。ドキュメント・テストにも実際のIP・名前を書かない（例にはRFC 5737のアドレスや`example.invalid`を使う）
- `.gitignore`で`.env`、鍵・証明書、`credentials*`、`*.mp4`、保存先ディレクトリ、状態ファイルを除外する
- GitHubのsecret scanningとpush protectionを有効にしている（リポジトリ設定）
- 実装の着手時に、CIで秘密情報の検出（gitleaksなど）と依存関係の脆弱性検査を行う
- ログにパスワードやAuthorizationヘッダを出さない。リクエストURLを出す場合も認証情報を含めない
- 録画ファイルはプライバシーに関わるため、テストデータやサンプルとしてもコミットしない

### カメラの時刻について

- カーソルの比較（`Datafrom`と`start_time`/`end_time`）は、カメラが返す時刻同士で行うため、実行環境との時刻ずれは取得の正しさに影響しない
- 実行環境の時計が影響するのは、初回実行時の`FETCH_INITIAL_LOOKBACK`（現在からのさかのぼり）だけ
- 仕様書には、現在時刻を取得するCGIは見当たらなかった（時刻は設定用の`set_basic`/`time`のみ）。HTTPレスポンスの`Date`ヘッダが取得できれば、起動時に実行環境との差を警告できる
- カメラの時計が過去に戻された場合、新しい録画の時刻がカーソルより前になり、取りこぼす恐れがある。連番は単調増加なので、連番を主キーにして`Datafrom`はカーソルの時刻より余裕（数時間）を持たせて遡る案がある
