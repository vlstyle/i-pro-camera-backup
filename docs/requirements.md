# このプロダクトで成し遂げること

## 目的

自宅に設置したPanasonic i-PROネットワークカメラ（WV-S1531L、WV-S3530）のSDカード録画を、カメラの公式CGI（[protocol.md](protocol.md)）で定期的に取得し、1動画を1ファイルとして保存する。保存先はローカルディレクトリまたはAWS S3。コンテナのワンショット実行（CLI、K8sのCronJobなど）を想定し、実行のたびに「前回の続き」から取得する。

## 設計の前提

- **1プロセスは1台のカメラだけを扱う**。複数のカメラを取得する場合は、プロセス（Pod）をカメラごとに分けて実行する
  - プログラム内に複数カメラの管理や、カメラ間の失敗の切り分けを持たない
  - カメラごとの実行間隔・失敗の影響・排他が独立する
- 1回の実行はワンショット（処理して終了）。常駐しない
- プログラム内ではリトライしない。失敗は非ゼロの終了コードで終了し、次回の実行（CronJobやコマンドの実行間隔）に任せる
- 設定はすべて環境変数で受け取る
- このリポジトリには、プログラム（ソース、テスト、コンテナイメージのビルド定義）と、K8sで動かすためのHelmチャート（`charts/i-pro-camera-backup/`）を置く。チャートは環境変数の組み立てやセキュリティ設定などアプリ側の契約を持つ。環境ごとの値（カメラの一覧・IP、保存先、IAMロールのARN、イメージタグ、Secret名）とArgo CDのApplicationは別リポジトリ（実行環境）で管理する

## 基本動作

1回の実行は次を繰り返す。

1. 取得位置（カーソル）を保存先から読む
2. カーソルより新しい録画のリストを取得する（`get_mp4_list`）
3. 古い順に1件ずつ、録画をダウンロードして保存先へ書く（`get_mp4_file`）
4. 保存に成功したら、カーソルを進めて保存先へ書く

- カーソルは「最後に保存した録画の`end_time`」（カメラが返す時刻）だけ。実行環境の時計とは比較しない
- 検索の`Datafrom`は、カーソルの`end_time`の秒を切り捨てて1秒足した時刻（例: `20260911T080005.99Z` → `20260911T080006Z`）。カメラは`end_time`が`Datafrom`以上の録画を返すため、最後に保存した録画が重複せず、次の録画から返る（[protocol.md](protocol.md)）
- 1回の検索は最大100件。100件に達したら、最後の`end_time`で再検索して続きを取得する
- 保存した後、カーソルを進める前に異常終了しても、次回は同じ録画を同じキーで上書き保存するだけで済む（冪等）
- 1件の保存に失敗したら、その回の処理を打ち切って非ゼロの終了コードで終了する（カーソルは進めない）。同じ録画で失敗し続けても、飛ばさずに止め続ける（原因調査を促す）
- カメラは同時に1つの検索・ダウンロードしか受け付けない（[protocol.md](protocol.md)）ため、直列に処理する
- 取得の開始位置は次のとおり
  - カーソルがある: カーソルの`end_time`の次の秒（上記）
  - カーソルが無い: 実行環境の現在時刻（UTC）の前日00:00:00。実行環境の時計を使うのはこの場合だけ（件数が多い場合は`FETCH_MAX_FILES`で複数回に分ける）
- 録画の種別（`_A`以外も）はそのまま取得する

## 保存先

保存先は`DEST_URL`で指定する。取り込みの処理は保存先の種類によらず共通で、保存先ごとに次の操作だけが異なる。

- 録画ファイルの書き込み
- カーソルの読み出し・書き込み
- 排他（二重実行の防止）

| 保存先 | `DEST_URL`の例 | 排他 |
|---|---|---|
| ローカルディレクトリ | `file:///data` | ロックファイル |
| AWS S3 | `s3://bucket/prefix/` | カーソルの条件付き書き込み（`If-Match`/`If-None-Match`） |

配置は保存先の種類によらず共通で、`DEST_URL`配下に置く。

| 内容 | 場所 |
|---|---|
| 録画 | `{DEST_URL}/{CAMERA_NAME}/{yyyy}/{yyyymm}/{yyyymmdd}/{ファイル名}` |
| カーソル | `{DEST_URL}/_state/{CAMERA_NAME}.json` |

- 録画のファイル名は、カメラが返す`{連番}_{yymmddHHMMSS}_{種別}.mp4`をそのまま使う。日付のディレクトリは、ファイル名のローカル時刻から決める
- 複数のカメラで同じ`DEST_URL`を共有できる（`CAMERA_NAME`で分かれる）
- 録画はストリーミングで書き込む。ローカルは一時ファイルに書いてからrenameで確定し、S3はマルチパートアップロードで送る。カメラからの応答を丸ごとメモリに載せない
- 圧縮はしない（約20%縮むが、削減は月数ドル規模で、直接再生できなくなるため）。保管料はS3のライフサイクル（安価なストレージクラスへの移行）で抑える

### カーソルの形式

```json
{"last_end_time": "20260911T080005.99Z"}
```

- 値はカメラが返す`end_time`の形式（UTC、小数秒は省略可）。ファイル名など他の値は持たない（保存したファイル名はログに出す）

### 初回の開始位置を指定したい場合

カーソルのファイル（`{DEST_URL}/_state/{CAMERA_NAME}.json`）を、開始したい時刻で作成してから初回を実行する。

### 録画の取り直し

- カーソルの`last_end_time`を取り直したい時刻に書き換えて実行する。次の実行は、その時刻の次の秒以降の録画から取得し、保存済みの録画は同じキーに上書きされる
- 取り直せるのは、カメラのSDカードに残っている録画だけ
- 取り直し専用の指定（`FETCH_RANGE_FROM`/`FETCH_RANGE_TO`でカーソルを読み書きせずに範囲を取得する）は、必要になれば将来追加する

### カーソルを保存先に置く理由

- 永続ストレージが無い環境（S3に保存するCronJobなど）でも、Podが毎回まっさらで前回の続きから取得できる。PVCが不要になる
- ローカルでもS3でも同じ設計になる
- 録画とは別のプレフィックス（`_state/`）にするため、録画側にライフサイクルの有効期限を設定してもカーソルが消えない
- カーソルが失われても、録画のキーが固定なので、さかのぼって再取得しても同じキーに上書きされるだけ（二重保存にならない）。範囲はカーソルの再作成（下記）で制御できる
- S3のオブジェクトメタデータは更新にコピーが必要なため、カーソルは本文にJSONで持つ

## カメラの時刻について

- カーソルの比較は、カメラが返す時刻同士で行う。実行環境の時計を使うのは、カーソルが無い初回の開始位置だけ（日単位の粗い指定のため、数分のずれは影響しない）
- カメラの時刻のずれや、時計が戻ったことの検知は、このプログラムの責務にしない（監視システムで検知する）
- カメラの時刻が実際とずれていると、保存先の日付ディレクトリや録画時刻も実際とずれる。カメラのNTP同期を設定しておくのが望ましい（このプログラムではカメラの設定を変更しない）

## 環境変数

`CAMERA_NAME`は`[a-z0-9_-]`のみとし、保存先のパスに使う。

| 変数 | 必須 | 既定値 | 内容 |
|---|---|---|---|
| `CAMERA_NAME` | ○ | - | カメラの名前（保存先のパスに使う） |
| `CAMERA_HOST` | ○ | - | カメラのホスト（必要ならポート付き） |
| `CAMERA_USER` | ○ | - | Basic認証のユーザーID |
| `CAMERA_PASSWORD` | ○ | - | Basic認証のパスワード |
| `DEST_URL` | ○ | - | 保存先（`file:///path`または`s3://bucket/prefix/`） |
| `DEST_S3_ENDPOINT` | | 未設定 | S3互換エンドポイントを使う場合のURL |
| `FETCH_MAX_FILES` | | `0`（無制限） | 1回の実行で保存する最大件数（実行時間の上限対策） |
| `FETCH_HTTP_TIMEOUT` | | `60s` | カメラへのHTTPリクエストのタイムアウト |
| `LOG_LEVEL` | | `info` | `debug`/`info`/`warn`/`error` |
| `LOG_FORMAT` | | `json` | `json`/`text` |

S3の認証とリージョンはAWS SDKの標準の環境変数（`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_REGION`など）に従う。

## 実行環境に求めること

- カメラのHTTP（LAN内）に到達できるネットワーク上で実行する
- 保存先がローカルディレクトリの場合のみ、書き込み可能な永続ディレクトリが必要。S3の場合は永続ストレージは不要
- 複数のカメラは、カメラごとに別のプロセス（Pod）として実行する。同じ`DEST_URL`を共有してよい
- 同じカメラのプロセスが二重に実行されないよう、実行環境側（CronJobの`concurrencyPolicy: Forbid`など）でも制御する。プログラム側の排他は保険

## 認証情報の取り扱い（publicリポジトリのため）

実ホスト・ユーザー・パスワード・AWSキーをコミットしない。次を実施する。

- 認証情報は環境変数でのみ受け取る。ファイルに書く設定方式は用意しない
- サンプルは`.env.example`に置き、値はダミー（`changeme`、`*.example.invalid`）にする。ドキュメント・テストにも実際のIP・名前を書かない（例にはRFC 5737のアドレスや`example.invalid`を使う）
- `.gitignore`で`.env`、鍵・証明書、`credentials*`、`*.mp4`、保存先ディレクトリ、状態ファイルを除外する
- GitHubのsecret scanningとpush protectionを有効にしている（リポジトリ設定）
- 実装の着手時に、CIで秘密情報の検出（gitleaksなど）と依存関係の脆弱性検査を行う
- ログにパスワードやAuthorizationヘッダを出さない。リクエストURLを出す場合も認証情報を含めない
- 録画ファイルはプライバシーに関わるため、テストデータやサンプルとしてもコミットしない

## 対象外

- ライブ映像の取得・配信
- カメラ設定の変更
- 動画の圧縮・再エンコード・解析
- 常駐プロセス（デーモン）化
- 1プロセスでの複数カメラの取得
- プログラム内のリトライ
- 手持ちの2機種以外の動作保証（動作確認は実機のみ）
